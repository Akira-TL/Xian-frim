# 《长安游迹 · AI寻迹吧唧》开发实施基线

本文档将[产品需求文档](长安游迹_AI寻迹吧唧_PRD.md)收敛为可执行的首版开发边界。产品需求文档仍是产品目标来源；本文档只记录当前代码与硬件事实、首个演示版本范围、验收条件和开发前必须确认的事项。

## 1. 当前工程事实

当前仓库是 MZ46-S3-DZ V1.0 圆形电子吧唧的 ESP32-S3 固件，不包含 K230 景区数字节点的软件工程。

| 能力 | 当前状态 | 可复用入口 |
|---|---|---|
| 360 × 360 圆形屏幕 | 已有 JD9855 QSPI 驱动和 LVGL 界面 | `main/boards/esp32s3-chat-badge/`、`main/display/` |
| 触控 | 已有 CST816D 驱动并接入 LVGL 输入设备 | `CustomBoard::InitializeTouch()` |
| 扬声器与语音 | 已有 VB6824 音频路径、音量控制和唤醒回调 | `main/audio/codecs/vb6824_audio_codec.*` |
| 页面与导航 | 已有页面注册、页面切换、首页和应用列表 | `main/display/page_manager/`、`main/display/page/` |
| 本地状态 | 已有非易失性存储（Non-Volatile Storage, NVS）封装 | `main/settings.*` |
| 素材存储 | 已有 microSD 挂载、图片读取和素材传输能力 | `main/boards/esp32s3-chat-badge/zw_sdcard.*`、`components/doit_min_program_upload/` |
| 网络 | 已有 Wi‑Fi、WebSocket、MQTT、UDP 和 HTTP 调用方 | `main/boards/common/wifi_board.*`、`main/protocols/` |
| NFC | 当前板级代码、硬件说明和组件中均未发现 NFC 读卡器驱动 | 尚无实现入口 |
| K230 管理端 | 当前仓库没有 K230 源码、模型、界面或部署脚本 | 需要独立工程或明确的单体仓库目录 |

## 2. NFC 交互口径

产品需求文档同时出现了三种不完全一致的描述：

1. 吧唧读取景点 NFC 节点；
2. K230 景区节点读取游客到达信息；
3. 吧唧端物料是 NFC 标签，景区端物料是 NFC 模块。

首版暂按与物料清单及现有硬件最一致的方案准备：

1. 吧唧携带被动 NFC 标签，用标签唯一标识游客或设备；
2. K230 景区节点携带主动 NFC 读卡模块；
3. 儿童仍以“用吧唧碰触景点节点”的方式完成交互；
4. K230 识别吧唧后，通过 Wi‑Fi 服务向对应吧唧发送景点解锁事件；
5. 吧唧收到事件后展示图片、故事和任务，并在本地记录进度。

该口径能避免在未确认硬件接口前给现有吧唧追加 NFC 读卡器。正式开发双设备通信前，必须由产品与硬件共同确认。

## 3. 首个演示版本范围

首个可演示版本只实现一条完整闭环，不同时铺开三个游戏、完整画像和真实景区规模预测。

### 3.1 吧唧端

- 首页显示探索值、已解锁景点数量和游戏入口；
- 内置一个示范景点“秦始皇帝陵博物院”；
- 收到景点解锁事件后展示景点图片、简短故事和任务入口；
- 实现一个仅依赖触控的《秦俑归阵》小游戏；
- 完成游戏后授予“秦俑守护徽章”，增加探索值；
- 重启后保留景点解锁、游戏完成和探索值；
- 在关键节点播放短提示音或故事音频。

### 3.2 K230 景区节点

- 读取一个演示 NFC 标签；
- 将标签映射到吧唧设备标识，将节点映射到景点 `XA001`；
- 向吧唧发送一次可重试、可去重的景点解锁事件；
- 显示当前到访数和最近到访记录；
- 使用演示数据展示未来 30 分钟区域压力和分流建议。

### 3.3 暂不进入首版

- 《长安寻宝》和《唐诗接龙》的完整玩法；
- 多景区部署、批量设备管理和账号体系；
- 基于真实大样本训练的游客聚类或人流预测模型；
- 在线内容编辑后台、支付、定位和家长端应用；
- 未经确认的吧唧端 NFC 读卡硬件改造。

## 4. 建议的数据与通信边界

### 4.1 吧唧本地状态

本地状态至少包含：

```json
{
  "schema_version": 1,
  "exploration_score": 10,
  "unlocked_spots": ["XA001"],
  "completed_games": ["qin_game"],
  "badges": ["qin_guardian"]
}
```

首版可使用单独 NVS 命名空间保存小型状态；图片和音频等大文件继续放在 microSD，不写入 NVS。

### 4.2 景点解锁事件

建议先定义与传输方式无关的事件，再决定使用现有 WebSocket 或 MQTT 通道：

```json
{
  "event_id": "node-xa001-000001",
  "type": "spot.unlock",
  "device_id": "badge-demo-01",
  "spot_id": "XA001",
  "occurred_at": "2026-10-02T13:30:00+08:00",
  "content_version": 1
}
```

`event_id` 用于重复投递去重；`content_version` 用于判断本地素材是否需要更新。儿童相关数据首版只使用随机设备标识，不采集姓名、联系方式或精确身份信息。

## 5. 开发阶段与完成门槛

### 阶段 0：固件基线可构建

- ESP-IDF 5.4.1 下完整构建通过；
- 当前 USB/JTAG 串口可读取芯片信息和启动日志；
- 不烧录前先保存现有设备信息和构建产物；
- 修复现有网络抽象依赖缺失，不将构建故障带入产品功能开发。

### 阶段 1：吧唧本地闭环

- 建立独立的探索状态模块，页面不直接读写零散 NVS 键；
- 完成首页、景点解锁页和《秦俑归阵》最小玩法；
- 支持模拟解锁事件，使无 K230 时也能演示完整流程；
- 断电重启后状态保持一致。

### 阶段 2：双设备闭环

- 确认 NFC 主动端、模块型号、总线和标签格式；
- 建立 K230 端最小服务；
- 完成节点读取、事件发送、吧唧确认和重复事件去重；
- 网络暂时中断时不丢失已经读取的到访事件。

### 阶段 3：管理展示与预测演示

- 展示至少两个区域的当前人数和最近到访；
- 用固定、可解释的演示数据计算 30 分钟压力；
- 明确标注演示预测，不宣称其来自未经验证的真实模型；
- 完成 PRD 中儿童互动、空间交互和景区管理三段演示。

## 6. 首轮验收场景

1. 新设备启动后进入“长安游迹”首页，探索值为 0；
2. 模拟或真实节点发送 `XA001` 解锁事件；
3. 吧唧在可接受时间内显示秦俑景点内容并播放提示音；
4. 用户通过触控完成《秦俑归阵》；
5. 首页探索值增加，秦俑徽章可见；
6. 重启设备后解锁状态和徽章仍存在；
7. 同一 `event_id` 再次发送时不会重复增加探索值；
8. K230 管理界面的到访数增加，并显示压力演示结果。

## 7. 开发前待确认

以下事项会实质影响实现，进入对应阶段前必须确认：

- NFC 主动读取方是否采用本文暂定口径；
- K230 开发板具体型号、操作系统或 SDK、NFC 模块型号及接线；
- K230 工程放入本仓库还是建立独立仓库；
- 吧唧与 K230 是否始终处于同一 Wi‑Fi 网络；
- 演示素材的图片、故事、音频和视觉稿是否已有可用版本及授权；
- “未来 30 分钟压力”的演示算法采用规则、回归模型还是预先生成结果；
- PRD 标题写“48 小时开发计划”，各阶段累计却达到 60 小时，实际比赛时限以哪一个为准。

## 8. 下一项可执行工作

先完成阶段 0 的固件基线构建。当前完整构建已通过蓝牙配置阶段，正在修复网络抽象组件缺失；基线构建稳定后，再以模拟解锁事件启动阶段 1，避免首个页面实现依赖尚未到位的 K230 和 NFC 硬件。
