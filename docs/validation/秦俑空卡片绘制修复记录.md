# 秦俑空卡片绘制修复记录

## 问题与根因

用户实物照片显示：游戏文字、按钮和卡片背景正常，但三片秦俑图片不可见。照片留在忽略目录 `logs/qin-empty-cards-real-photo.jpg`，不纳入仓库。

压缩素材本身没有损坏。此前只启用 `CONFIG_LV_USE_RLE=y`，遗漏 `CONFIG_LV_BIN_DECODER_RAM_LOAD=y`；LVGL 在压缩图片的真正绘制阶段拒绝解码，报告 `Need LV_BIN_DECODER_RAM_LOAD to be enabled`。图片对象成功创建不等于图片成功绘制。

此前四张图片逐像素解压一致的检查只能证明压缩数据正确，不能证明完整绘制路径可用；本次实物反馈收窄了此前检查的结论。

## 真实绘制回归

用户明确同意在真实图片绘制入口测试。`scripts/test-qin-render.sh` 使用项目实际 LVGL、生产 `qin_art_add` 和正式生成素材，以内存屏替换物理显示输出，不替换图片绘制代码。解码开关读取实际固件构建目录的 `sdkconfig`，不硬编码正确配置。

- 修复前：头部图片相对空卡片改变 0 个像素，测试失败；日志 `logs/qin-render-regression-red.log`。
- 只补齐内存加载开关后：改变 1277 个像素，测试通过；日志 `logs/qin-render-regression-green.log`。
- 临时诊断重复旧配置仍为 0 个像素；保持图片、布局和调用不变，单独开启缺失配置后恢复。

当前回归只断言头部图片可见，不宣称覆盖四张图片的完整绘制、设备内存压力、圆屏边缘或实物触摸。四图解压一致性属于另一个检查。实物图片恢复仍须烧录后确认。

## 修复范围与固件

保留既有低分辨率素材和无损压缩，仅补齐默认解码配置及当前构建配置，不修改拖拽、进度保存或蓝牙协议。

实际构建头文件确认两个开关均为 1。固件大小 `0x3d1a10` 字节，应用分区剩余 36%；SHA-256：
